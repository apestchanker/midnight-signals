Three developments connect this edition: more capable contracts, infrastructure
for generating private proofs, and an easier way to use applications. Their
release stages differ. **Research cutoff: November 17, 2026.** “Late November”
is the edition name; it does not imply coverage of events after that date.

## 1. Ledger 9: contracts can work together

📅 **Mainnet hard fork: November 6 · Client patch: November 17**

Midnight upgraded Mainnet from Ledger 8 to Ledger 9, carrying existing balances
and deployed contracts forward. The change gives applications shared building
blocks: one contract can invoke another, identify its caller and publish events
that interfaces and indexers can follow.

The release also brings ECDSA authorization and BIP-44 address derivation for
wallet and custody integrations. **Keccak-256 is a hash function; ECDSA is a
signature scheme.** These primitives help developers build integrations, but
their availability does not mean every bridge or custody product is already live.

Source: [Mainnet upgrade announcement](https://midnight.network/blog/ledger-9-upgrade-on-mainnet).

### Which roadmap promises have arrived?

| Capability | Status at the cutoff |
| --- | --- |
| Contract calls, caller identity and events | Delivered; the first phase of calls and events is unshielded. |
| ECDSA, native secp256k1 and Keccak | Available building blocks for integrations. |
| ZKIR v3 | Delivered in the proving and compiler stack. |
| Fully private composability | Still a Q1 2027 roadmap target. |
| Enterprise Ed25519 / P-256 key support | Roadmap target: Q4 2026. |
| In-contract and recursive proof verification | Roadmap target: Q4 2026. |
| BABE Mainnet migration, staking and community block production | Roadmap target: Q1 2027. BABE staged migration is targeted for Q4 2026, with Mainnet migration beginning in Q1 2027. |

This is a comparison of the [upgrade scope](https://docs.midnight.network/relnotes/ledger-9)
with the [official roadmap](https://midnight.network/roadmap), not a declaration
that every item scheduled for Q4 has shipped.

### What builders need to do now

The **November 17 client patch** leaves the chain on Ledger 9.1.0.1. The recommended
set includes Midnight.js **5.0.1**, Wallet SDK **2.0.1**, Compact toolchain
**0.36.1** and proof server **9.0.2**. This patch does not require contract
recompilation or redeployment. Preview reset on November 7; Preprod upgraded
in place on November 9. The cNIGHT–mNIGHT bridge still requires a separate
governance activation, and block-production rewards are outside this upgrade.
See the [migration guide](https://docs.midnight.network/relnotes/ledger-9)
and [compatibility matrix](https://docs.midnight.network/relnotes/support-matrix).

Treat application migration and contract recompilation as separate tasks.
Midnight.js 5 uses ESM and changes provider configuration and ledger-era handling;
update integrations against its [release notes](https://docs.midnight.network/relnotes/midnight-js/midnight-js-5-0-0).
Recompiling older contracts for ZKIR v3 changes their verifier keys, even if their
source stays the same. Follow the maintenance-authority or redeployment path
appropriate to that contract; see the [Compact 0.36 release notes](https://docs.midnight.network/relnotes/compact/toolchain-0.36.0).

## 2. Google Cloud: generating proofs inside a protected environment

📅 **Reviewed November 17 · Source type: customer case study**

The Google publication is a **Google Cloud customer case study**, rather than
an academic paper. It describes Midnight Foundation and BCW Group moving
computationally intensive ZK proving into confidential cloud infrastructure,
using Confidential Space and GKE Confidential Nodes.

Google reports a two-month journey from concept to production and says
attestation addressed prerequisites for commercial wallet integrations,
including Lace. This is deployment evidence attributed to the participants,
not an independent performance benchmark. The cited “under one minute” result
concerns developer onboarding, not transaction finality or proof-generation
latency. Source: [Google Cloud's Midnight case study](https://cloud.google.com/customers/midnightfoundation).

### What a TEE contributes

A **Trusted Execution Environment** isolates computation so approved software
can process sensitive inputs while protecting them from the infrastructure
operator. **Remote attestation** supplies evidence about the environment and
workload; an access policy decides whether that workload may receive secrets.
The approved program itself still processes the private data.

In this conceptual proving flow, the TEE protects inputs during computation,
while the ZK proof lets Midnight verify the resulting claim without receiving
those private inputs. These are different responsibilities. Hardware isolation,
the approved code and the attestation service remain part of the trust model.
Source: [Confidential Space architecture](https://docs.cloud.google.com/confidential-computing/confidential-space/docs/confidential-space-overview).

### What to expect—and what remains to measure

The intended benefit is a lighter workload for phones and laptops, with remote
capacity that can scale as demand rises. The case study supports that direction,
but publishes no comparable before/after proving-latency benchmark. It also
does not establish that every Lace transaction already uses this service.

For builders, the practical evaluation is concrete: verify which code receives
inputs, how attestation is checked, what data can leave the workload, and how
failure or unavailable capacity affects the user experience. Faster infrastructure
only improves the product when those boundaries are explicit.

## 3. Midnight Passport: passkeys, accounts and limited permissions

📅 **As of November 17 · Experimental demo; SDK planning/specification stage**

Passport aims to make using Midnight applications feel closer to signing into
a familiar service. Its design combines passkeys, a named account and an
**Account Custody Contract (ACC)** that holds funds and enforces authorization.
An application receives permission to perform specified actions; it does not
need to become the owner of the user's account.

The upstream [Passport SDK repository](https://github.com/midnightntwrk/midnight-passport-sdk)
still describes a planning/specification stage and a defined reduced beta.
Its intended packages serve account owners, integrating dApps and agents.
That is a development direction, not a generally available production SDK.

### How the intended experience works

1. **Create an account with a passkey.** The specification targets a named
   account such as `alice.passport.night`, with onboarding handled by Passport
   when a dApp redirects a new user there.
2. **Approve a bounded grant.** A passkey approval authorizes an application
   or agent within specified operations, spending limits and an expiry.
   Subsequent permitted actions need not request another approval every time.
3. **Keep control.** Owners can revoke grants. Device management, encrypted
   backups and recovery belong to the broader account experience. Access to
   private state or viewing keys requires its own consent.

The design also allows DUST sponsorship or capacity services, so users need
not manage DUST directly in that experience. Someone still supplies the
execution resources. These are **specified capabilities**, not a claim that
all flows work in the current demo. Source: [SDK requirements](https://github.com/midnightntwrk/midnight-passport-sdk/blob/main/docs/sdk-requirements.md)
and [Passport product plan](https://midnightntwrk.github.io/passport/site/plan.html).

### Who can use it now?

**Developers and testers can explore the experimental prototype**, with
compatible passkey support and a Stagenet setup. The
[demo repository](https://github.com/midnightntwrk/passport-demo) links to
[midnightpassport.com](https://midnightpassport.com) and provides local setup
instructions. Its current [network configuration](https://github.com/midnightntwrk/passport-demo/blob/main/examples/passport-demo/src/lib/networks.ts)
allows transactions and name claims only on **Stagenet**.

The project's [prototype description](https://github.com/midnightntwrk/passport-demo/blob/main/WHAT-THIS-IS.md)
labels it experimental and unaudited. It is not a Mainnet wallet for real funds.
The reviewed sources do not confirm a public production launch date, an eligible
consumer cohort or immediate Mainnet access. The roadmap's Passport milestones
are targets, not an access invitation.

The next useful release evidence will be a published SDK, documented network
support, audited account and recovery behavior, and a confirmed user-access
path. Until then, Passport offers a concrete prototype and a detailed product
specification to evaluate.
