The first half of August brought some important developments for builders
working on Midnight. Rather than major protocol announcements, these weeks were
mostly about maturing the developer stack, addressing issues discovered through
real-world usage, and providing better reference patterns for privacy-preserving
applications.

Here are two technical updates worth highlighting.

## 1. Important Wallet SDK change: migrate away from sub-package imports

This is probably the most immediately relevant update for developers currently
building on Midnight.

The Midnight team reported that several apparently unrelated problems —
constructor errors, `ChargedState` errors, and even heap out-of-memory (OOM)
crashes — actually shared the same root cause: the old pattern of importing
Wallet SDK components separately, such as:

- `wallet-sdk-shielded`
- `wallet-sdk-facade`
- `wallet-sdk-hd`

That import pattern should no longer be used.

The recommended solution is to migrate to the consolidated package:

```
@midnight-ntwrk/wallet-sdk@1.2.0
```

This consolidation simplifies dependency management and avoids compatibility
problems between the previously separate Wallet SDK packages.

There is also an important change for developers starting a new Midnight project:
`example-counter` was archived during the week, and `example-hello-world` is now
the recommended reference implementation.

> Official `example-hello-world` repository — under the `midnightntwrk` GitHub org.

### A DUST issue developers should be aware of

The team also documented a known wallet state lifecycle issue.

When a submitted transaction is rejected by the ledger with:

```
1014 — InvalidDustSpendProof
```

the associated DUST note can remain locally marked as spent even though the
ledger rejected the transaction.

There is currently no SDK fix.

The recommended workaround is to snapshot the wallet state before submitting the
transaction and restore it if the transaction is rejected.

For applications managing transactions programmatically, this is an especially
important edge case to handle.

*Source: Midnight Dev Status Update, Aug 8–14.*

## 2. ZKLoan: a reference example much closer to a real privacy application

Another interesting development is **ZKLoan Credit Scorer**, an official example
that moves significantly beyond the traditional counter-style smart contract.

> Official ZKLoan repository — published under the `midnightntwrk` GitHub org.

ZKLoan demonstrates a credit assessment system where sensitive information such
as credit score, income, and customer history can remain private, while the
outcome of the assessment can still be verified using Zero-Knowledge Proofs.

At a conceptual level, it demonstrates one of Midnight's fundamental
architectural patterns:

```
Private State → Off-chain execution → ZK Proof → Verification → Public State
```

The underlying financial information does not need to be disclosed on-chain for
the application to prove that the required conditions were satisfied.

But what makes ZKLoan particularly useful for developers is that it demonstrates
patterns much closer to those required by real applications.

These include Schnorr-signed attestations over Jubjub, verification of those
attestations inside ZK circuits, nested public-state maps, and state migrations
performed across multiple transactions.

One particularly interesting example is changing a user's PIN.

Because Compact circuits need computational workloads that can be determined at
compile time, they cannot simply iterate over collections of unknown size.
ZKLoan addresses this by processing records in fixed-size batches, while on-chain
state tracks the progress of the migration.

This is a useful design pattern for understanding how larger state transitions
can be implemented while respecting the constraints of ZK circuits.

The repository also provides a useful snapshot of the current developer stack,
including Compact 0.31.1, Midnight.js 4.1.x, Ledger 8.1, and Wallet SDK 1.2.0.
