## 1. The Cardano→Midnight bridge became documented and testable

### Where the specification lives

This bridge has no numbered MIP. The original proposal was filed twice — issues
#20 and #21 — and both were closed.

The specification lives in the node repository, and this is what changed during
the window: on 15 July, PR #1857 added a documentation set that did not
previously exist.

| Document | Purpose |
| --- | --- |
| `docs/c-to-m-bridge.md` | Concepts: transfer classes, pallet split, configuration |
| `docs/c-to-m-bridge-walkthrough.md` | Hands-on happy-path guide against Stagenet |
| `docs/c-to-m-bridge-enabling.md` | How to check whether the bridge is on, and how to switch it on |

The executable reference for the flow is the end-to-end test
`tests/e2e/tests/c2m_bridge.rs` (`bridge_transfer_cnight_to_midnight_address`);
the walkthrough defers to it wherever the two diverge. The implementation sits in
`pallets/c2m-bridge/`, layered on `pallet-bridge`, the Cardano-observation
foundation contributed by IOG.

### What the bridge does

It moves cNIGHT (Cardano-native NIGHT) to mNIGHT (Midnight-native), in one
direction only. It is not a wrapped asset: the design preserves NIGHT's role as
the generator of DUST, which a wrapper would break. Verification comes from the
Midnight node's own Cardano observation rather than an external validator set, so
security is inherited from Cardano — at the cost of latency, since a lock is
credited only after Cardano's 432-block stability window.

Four transfer classes are distinguished, and three of them route funds to the
Treasury rather than to a user:

- **User Transfers** — cNIGHT locked at the ICS validator address by anyone other
  than the Reserve Validator, with a recipient encoded in Cardano metadata label
  `6500973`. This is the claimable path.
- **Reserve Transfers** — Reserve Validator to ICS, releasing mNIGHT from the
  Midnight Reserve to pay block rewards.
- **Subminimal, Invalid and Unapproved Transfers** — locks below the fee
  threshold, locks with malformed or missing recipient metadata, and locks whose
  Cardano transaction hash is not on the approved allow-list. All are credited to
  the Midnight Treasury.

### Activation status

The on/off switch is the Bridge pallet's `dataCheckpoint` storage. While it is
empty the observer never starts, and cNIGHT locked on Cardano is never seen. It
is set in one of two ways:

- dev and local-environment chains bake `initial_checkpoint` into genesis, so the
  bridge is live from block 0.
- Mainnet and Stagenet ship with it unset, deliberately, so that Stagenet
  rehearses the live-chain enable procedure mainnet will require. It is switched
  on later through the Root-origin call
  `bridge.setMainChainScripts(newScripts, dataCheckpoint)`.

As of 4 August 2026, Stagenet's `bridge.dataCheckpoint` holds a non-empty value,
so the bridge is live there. Stagenet runs node `2.0.0-d9729c13`. Current status
can be checked at any time in Polkadot-JS Apps under Developer → Chain state →
`bridge.dataCheckpoint()`: an empty value means disabled, a `Tx(0x…)` or
`Block(n)` value means live.

### How to test it

Locally, there is nothing blocking. On dev and local-environment chains the
bridge runs from genesis and the operator holds Root, so the full flow is
available. This is the path of least friction.

On Stagenet, one step requires the node team. The sequence is
prepare → approve → submit → wait → claim:

1. Derive the recipient address:
   `midnight-node-toolkit show-address --network stagenet --seed <32-byte hex> --user-address`.
2. Build but do not submit the Cardano lock with `cardano-cli` — cNIGHT to the
   ICS address, recipient under metadata label `6500973` — then read the
   transaction hash from the unsigned body. Signing does not change the hash,
   which is why the build precedes the approval.
3. Pre-approve that hash through governance (`add_approved_mc_tx_hashes`).
4. Sign and submit the lock to Cardano, then wait 432 Cardano blocks.
5. Observation emits `C2MBridge::UserTransfer` and `DistributeNight(CardanoBridge)`,
   crediting a claimable balance.
6. Claim with `ClaimRewards(CardanoBridge)`, a ZK transaction, producing a fresh
   NIGHT UTXO of the amount minus fee.

> **NOTE:** Step 3 is the constraint. `add_approved_mc_tx_hashes` is a
> Root-origin call; on Stagenet that means a Council plus Technical Committee
> motion driven with the governance keys of the seven permissioned validators,
> which external developers will not hold. The consequence of skipping it is not a
> failed transaction: a hash that is not approved by the time Midnight observes
> the lock is swept to the Treasury as an Unapproved Transfer, and the test
> tokens are lost. The concepts document describes the allow-list as a temporary
> measure planned for removal.

The toolkit's one-shot `bridge-transfer` command builds, signs and submits in a
single call and prints the hash only afterwards, so it cannot feed the approval
ahead of time and races the observation window.

Stagenet parameters, from the genesis chain-spec: Cardano Preview; cNIGHT policy
`d2dbff62…` with an empty asset name; bridge fee 5 percent (500 basis points);
minimum user transfer 1000 STAR; stability window 432 blocks. Amounts are
denominated in STAR on both chains, as the pallet does not re-denominate. Test
cNIGHT is available from the Midnight faucet and Preview ADA from the Cardano
testnets faucet.

### The integration surface

Indexer `v4.4.0-rc.1` (22 July) exposes the bridge to applications, with every
bridge type, query and subscription marked `@beta`: queries `bridgeEvents`,
`bridgeDeposits`, `bridgeReserveInflows`, `bridgeTreasuryInflows`,
`bridgePoolSummary` and `bridgeBalance`, plus subscriptions `bridgeEvents`,
`bridgePoolUpdates` and `bridgeBalance`. One design detail matters for
integrators: claims have no dedicated query. `BridgeClaimTransaction` implements
the standard `Transaction` interface, so a wallet already watching
`unshieldedTransactions(address)` sees them correctly typed.

Node `2.1.0` (31 July) added the `get_bridge_receiving_amount` host API, along
with a security fix (PR #1513) of broader interest: the bridge previously
classified transfers using Cardano transaction metadata, which opened an attack
on the reserve pool. Classification now distinguishes Reserve Validator inputs
from ICS Validator inputs. The underlying lesson — attacker-controlled metadata
cannot serve as a trust-bearing classifier — applies well beyond this codebase.

### What this means today

The bridge is useful now for wallet, explorer and indexer integrators: the
GraphQL surface is queryable in beta and Stagenet is live, so applications can be
built and exercised against a real flow.

It is not yet ready for a production integration, for three reasons. The
`c2m-bridge` pallet exists only in the Node 2.x runtime, a fresh-chain line that
mainnet does not run. Unilateral testing on Stagenet is gated by the governance
allow-list. And with no numbered MIP or public documentation, the design remains
subject to change.

### Unrelated: the Wanchain bridge exploit

Unrelated to Midnight's own protocol. On 21 July a third-party bridge operated by
Wanchain between Cardano and BNB Chain was exploited for roughly 515 million
NIGHT. According to reporting citing analysis by BlockSec, the root cause was a
non-injective signed-message encoding in the bridge's `TreasuryCheck` validator:
14 variable-length redeemer fields concatenated with no separators or length
prefixes, allowing a legitimate signature to be replayed for a larger transfer.
The Midnight Foundation stated that Midnight's validators, consensus and core
protocol were not involved.

## 2. The npm scope is moving to @midnightntwrk, and the wallet SDK has already left the old one

The Ledger `8.1.1` release notes, dated 31 July and published 4 August, list a
breaking change: packages are now published under the `@midnightntwrk` scope,
dropping the hyphen from `@midnight-ntwrk`. For example,
`@midnight-ntwrk/ledger-v8` becomes `@midnightntwrk/ledger-v8`. There are no API
changes; the package name is the only thing that moves.

Registry state as of 4 August 2026:

| Package | `@midnightntwrk` (new) | `@midnight-ntwrk` (old) |
| --- | --- | --- |
| `wallet-sdk` | 1.2.0 | 1.1.0 |
| `wallet-sdk-facade` | 4.1.0 | 4.0.1 |
| `wallet-sdk-shielded` | 3.0.2 | 3.0.1 |
| `wallet-sdk-prover-client` | 1.2.3 | 1.2.2 |
| `dapp-connector-api` | 4.1.0-canary | 4.0.1 |
| `ledger-v8` | 8.1.1 | 8.1.1 |
| `wallet-sdk-unshielded-wallet` | 3.1.0 | 3.1.0 |
| `wallet-sdk-testkit` | 0.2.0 | 0.2.0 |
| `compact-runtime` | not published | 0.16.0 |
| `midnight-js`, `midnight-js-contracts`, `midnight-js-types`, `midnight-js-network-id`, `midnight-js-utils` | not published | 4.1.1 |
| `zswap`, `onchain-runtime`, `ledger` | not published | 4.0.0 / 0.3.0 / 4.0.0 |
| `wallet`, `wallet-api` | not published | 5.0.0 |
| `compact-js` | not published | 2.5.3 |

Three conclusions follow, and they pull in different directions.

**This is a migration in progress, not a cutover.** The Midnight.js family, the
Compact runtime, Zswap, the on-chain runtime and Compact.js do not exist on the
new scope at all. A blanket find-and-replace across `package.json` will break the
install.

**For the wallet SDK, staying on the old scope now costs versions.** The newest
stable releases of `wallet-sdk`, `wallet-sdk-facade`, `wallet-sdk-shielded` and
`wallet-sdk-prover-client` were published to the new scope on 19 June, while the
old scope's latest tag still points at builds from 27 May. Both scopes continue
to receive canary publishes, as recently as 4 August, so the old scope is not
dormant — but its stable line has fallen a minor version behind.

**The announcement lags the change.** The new scope has been receiving publishes
since mid-June; the 4 August Ledger `8.1.1` note is the first time it was flagged
as a breaking change.

Recommended handling: migrate one package at a time rather than in bulk, confirm
each name resolves before committing, and start with the wallet SDK, where the
two scopes have actually diverged.

Ledger `8.1.1` is otherwise a non-event for application developers: added array
test coverage and clippy lint cleanups, with no protocol, serialization or API
behaviour changes for well-formed transactions.

## 3. The MIP process has become the venue for protocol and standards work

The Midnight Foundation published a post on the improvement-proposal process on
4 August, but the stronger signal is the repository itself, which saw sustained
activity throughout the window.

Two document types are in use, and the distinction matters:

- **MPS** — Midnight Problem Statements are solution-agnostic descriptions of
  friction, gaps or opportunities. They define *what* needs solving.
- **MIPs** — Midnight Improvement Proposals are concrete, technically precise
  proposals. They propose *how*.

The process document governing MPS submissions, MPS-0001, was itself merged on
29 July, so this two-track split is newly formalised rather than
long-established.

The lifecycle, from MIP-0001: Draft → editors assign a number → Proposed →
community commentary of at least two weeks → editor vote → Accepted →
implementation work → Implemented → network upgrade deployment → Active. Where a
proposal terminates depends on its category: Informational MIPs are final at
Accepted, Governance MIPs at Implemented, and Core, Standards and Networking MIPs
at Active. Withdrawn and Superseded exist as exceptional transitions.

Merged during the window:

| 14 Jul | MPS-0028: Pre-Finality State Visibility for Indexer and Wallet |
| 14 Jul | MPS-0029: Caller Identity Access in Compact Circuits |
| 15–17 Jul | MIP-0012: Contract Custody of Midnight-Native Assets |
| 15–17 Jul | MIP-0013: Multi-key Account Authorisation for Custody Contracts |

| 4 Aug | MPS-0031: DUST Grant DAO |
| 4 Aug | MPS-0032: Storage Growth |

Also opened, on 3 August: a draft MIP for Committee Bridge Consensus
Integration, specifying the Midnight-to-Cardano return path — a Cardano light
client that tracks the Midnight BEEFY committee by induction and verifies
committee-signed MMR roots, giving Cardano contracts Merkle-inclusion proofs of
Midnight blocks. It is standard Polkadot BEEFY plus a seat-weighted committee
commitment sized to fit Cardano's transaction limits. It remains an unnumbered,
open pull request.

Token standards are consolidating into a coherent family: MIP-0004 (fungible
token with UTXO), MIP-0011 (native shielded token) and now MIP-0014 (native
unshielded token). For anyone designing a token contract, these are the
documents to track. The registry currently holds 14 numbered MIPs and 32
numbered MPS entries.

Two contribution rules are easy to miss:

- The repository requires **verified commit signatures**. Unsigned commits are
  labelled `BLOCKED | Unverified` and cannot be merged until every commit on the
  pull request is signed.
- Pull requests are expected to **describe a change, not implement it**, linking
  to code repositories rather than inlining implementation. Drafting with AI
  tooling is explicitly permitted, but commits must be authored by the
  responsible human; configuring an AI assistant as author or co-author is not
  allowed, since the named author is accountable for the content.

For anything that is a standard rather than a bug — token semantics, caller
identity in Compact, custody models, storage growth — this repository, rather
than the issue trackers, is where the decision now happens. The two-week
commentary window is the practical opportunity to influence a proposal before
the editor vote.

## Also of note

**No compiler changes this window.** The Compact toolchain remains `0.31.1`
(Compact language `0.23.0`), tagged 25 June 2026. Nothing newer shipped during
the last three weeks, and `pragma language_version >= 0.23;` remains correct for
new contracts.

**Indexer `4.4.0-rc.1`, beyond the bridge:** public contract events and CCC
execution-inputs queries, HTTP response and subscription WebSocket compression,
per-block DUST merkle roots, storage-core `gc-v1` with a ledger-state retention
window, and a fix for contract-action `unshieldedBalances` always returning
empty.
